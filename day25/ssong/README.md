# Day 25 - Stateful vs Stateless

# Stateful (상태유지)

클라이언트와 서버 관계에서 서버가 클라이언트의 상태를 보존하는 것

예를 들어 한번 로그인하면 페이지를 이동해도 로그인이 유지되는 것이 바로 서버가 클라이언트의 상태를 유지하고 있기 때문이다. 클라이언트의 정보는 일반적으로 브라우저의 쿠키나 서버 세션에 저장되어 관리된다.

대표적으로 Stateful 구조를 따르는 프로토콜로는 TCP가 있다.

TCP의 3-way-handshake 과정을 통해 클라이언트와 서버가 서로 established된 **상태**가 된다. 이 상태가 되어야 클라이언트와 서버가 서로 데이터를 주고 받을 수 있다.

Stateful의 문제점은 서버가 클라이언트의 정보를 저장하고 있다보니 서버가 멈추거나 못쓰게되어 다른 서버를 써야되면 새로운 서버는 기존 상태를 알 수가 없다. 이로 인해 다시 로그인을 해야하는 상황이 생긴다. 실서비스의 경우 이러한 문제를 막기 위해 클라이언트의 상태 데이터를 따로 Redis 등의 캐시 서버에 저장하여 이용한다.

# Stateless (무상태)

서버가 클라이언트의 상태를 보존하지 않음

Stateless 구조에서는 서버가 단순히 요청에 대한 응답만 보낼 뿐 상태 관리는 전적으로 클라이언트에게 맡긴다.

대표적인 프로토콜로는 UDP와 HTTP가 있다. UDP의 경우 TCP와 달리 Handshake 과정 없이 데이터를 바로 전송할 뿐 클라이언트의 정보를 저장하지 않는다.

Stateless의 문제점은 클라이언트의 요청에 상대적으로 Stateful 보다 더 많은 데이터가 소모된다는 점이다. 로그인을 해야 접근 가능한 리소스의 경우 클라이언트가 매 요청마다 자신의 정보를 담아서 보내서 인증을 해야하기 때문이다.
