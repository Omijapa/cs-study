# SQL vs NoSQL

### SQL (Structured Query Language)

> 테이블 기반의 관계형 데이터베이스

- 데이터를 행과 열 형태로 저장
- 테이블 간 관계를 외래키로 표현
- SQL을 이용해 데이터를 조회 및 조작
- 대표적인 DB로는 MySQL, PostgreSQL, Oracle 등이 있다.

#### 특징

1. 정해진 스키마 : 테이블의 구조가 미리 정의됨
2. ACID 보장 : 트랜잭션의 안정성을 보장함
3. JOIN 지원

#### 장점

- 데이터 무결성 높음
- ACID 트랜잭션 보장
- JOIN
- 복잡한 조회에 적합

#### 단점

- 스키마 변경이 어려움
- 수평 확장이 상대적으로 어려움
- 데이터 구조가 자주 바뀌는 서비스의 경우 유연성이 떨어짐

### NoSQL

> 관계형 모델을 사용하지 않는 다양한 형태의 데이터베이스

- 대표적으로 MongoDB (Document), Redis(Key-Value), Cassandra(Column Family), Neo4j(Graph)

#### 특징

1. 스키마가 자유롭다 : 데이터가 특정 구조를 가지지 않아도 됨
2. 수평 확장이 쉽다 : 데이터를 분산 저장하기 때문에 대규모 트래픽 처리에 적합함
3. JOIN을 거의 사용하지 않는다 : 이미 필요한 데이터를 한 Document 안에 함께 저장하는 경우가 많아 JOIN보다 조회 속도가 빠른 편

#### 장점

- 스키마 변경이 자유로움
- 대용량 데이터를 쉽게 분산 저장할 수 있음
- 대체로 읽기 성능이 뛰어남
- 확장성이 좋음

#### 단점

- JOIN 기능이 제한적임
- 데이터 중복이 발생할 수 있음
- 데이터 일관성을 위해 추가 관리가 필요함

# Anomaly

> 데이터 중복으로 인해 데이터 삽입, 수정, 삭제 과정에서 의도하지 않은 문제가 발생하는 현상

### 삽입 이상

> 불필요한 데이터가 없으면 원하는 데이터를 삽입할 수 없는 문제

예를 들어, 다음과 같은 테이블이 있다고 하자

| 학생ID | 학생명 | 학과 | 교수명 |
| ------ | ------ | ---- | ------ |
| 1001   | 김철수 | 컴공 | 홍길동 |
| 1002   | 이영희 | 컴공 | 홍길동 |
| 1003   | 박민수 | AI   | 김교수 |

새로운 학과가 생겼지만 아직 학생이 없는 경우 학생 정보가 없어 행 자체를 추가할 수 없다

즉, 학과 정보만 저장할 수 없고 반드시 학생 정보도 함께 입력해야한다. 이것이 삽입 이상!

| 학생ID | 학생명 | 학과 | 교수명 |
| ------ | ------ | ---- | ------ |
| ?      | ?      | 보안 | 최교수 |

### 갱신 이상

> 같은 데이터를 여러 곳에서 수정해야 하는 문제

예를 들어 홍길동이라는 교수 대신 홍길순이라는 사람으로 바뀐 경우, 정규화가 되어 있지 않아 모든 행을 수정해야 한다. 만약 한 행만 수정하게 되면 동일한 학과의 교수명이 서로 다르게 저장되는 데이터 불일치가 발생한다.

### 삭제 이상

> 필요한 데이터를 삭제했는데 원하지 않는 정보까지 함께 삭제되는 문제

예를 들어 다음과 같이 학과에 학생이 한 명만 있다고 하자.

| 학생명 | 학과 | 교수명 |
| ------ | ---- | ------ |
| 박민수 | AI   | 김교수 |

여기서 박민수 학생의 데이터를 지우면 학과와 김교수에 대한 정보도 함께 삭제된다. 이것이 삭제 이상!

그럼 이러한 이상현상은 왜 생기는 것일까?

가장 큰 원인은 데이터 중복이다. 하나의 테이블에 여러 정보를 함께 저장하면, 정보가 반복되고 그 결과 다양한 어노멀리가 발생한다.

이를 위한 해결책으로는 정규화를 통한 데이터 중복 제거가 있다.

# Index

> 데이터베이스에서 원하는 데이터를 빠르기 찾기 위한 자료구조

책에 있는 목차(Index)와 같은 개념으로 테이블 전체를 탐색하는게 아니라 인덱스를 활용해 원하는 데이터의 위치를 빠르게 찾을 수 있음

현대의 관계형 데이터베이스들은 대부분 B+Tree 자료구조를 사용하여 인덱스를 관리한다.

- B+Tree
  - B-Tree를 개선한 형태로, 실제 데이터는 리프 노드에만 저장하고 내부 노드는 검색을 위한 키만 저장함
  - 트리의 높이가 낮아 탐색 속도가 빠름
  - 모든 리프노드들은 연결 리스트의 형태로 구성되어 있음
  - 탐색 시간은 O(log N)
    더 자세한건 [여기서](https://velog.io/@emplam27/%EC%9E%90%EB%A3%8C%EA%B5%AC%EC%A1%B0-%EA%B7%B8%EB%A6%BC%EC%9C%BC%EB%A1%9C-%EC%95%8C%EC%95%84%EB%B3%B4%EB%8A%94-B-Plus-Tree)..

#### 장점

- 검색 속도가 빠르다
- Full Table Scan을 줄일 수 있다
- JOIN 성능이 향상된다
- 대용량 데이터에서 효과가 크다

#### 단점

인덱스는 조회 성능을 높이는 대신 쓰기 성능과 저장 공간을 희생한다

- 새로운 데이터 추가 시 인덱스도 함께 갱신해야 함 (인덱스 재정렬)
- 인덱스 컬럼 변경 시 기존 인덱스 삭제 및 새로운 인덱스 생성이 필요함
- 삭제 시에 인덱스 엔트리를 함께 제거해야 함
- 인덱스를 저장하기 위한 별도의 저장공간이 필요함

Q. 인덱스는 많을 수록 좋은가

놉. 조회 성능안 향상되지만 삽입, 수정, 삭제에 있어서는 성능 저하가 발생하고 저장공간도 추가적으로 필요함. 따라서 조회가 자주 발생하는 컬럼에 필요한 만큼만 생성하는 것이 좋음

Q. 어떤 컬럼에 주로 생성함?

WHERE 조건에 자주 사용되는 컬럼이나 JOIN컬럼, ORDER BY, GROUP BY 컬럼, 선택도가 높은 컬럼에서 주로 생성함
